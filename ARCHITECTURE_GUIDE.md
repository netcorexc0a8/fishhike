# 📐 FishHike: Руководство по Архитектуре (Clean Architecture & BLoC)

Это руководство определяет правила организации кода для обеспечения тестируемости, масштабируемости и простоты поддержки.

## 1. Общие Принципы

1.  **Clean Architecture:** Проект разделён на три основных слоя: Presentation, Domain и Data.
2.  **Зависимость:** Зависимости всегда направлены внутрь (Presentation -> Domain -> Data). Domain не должен знать о Presentation или Data.
3.  **Модульность:** Код разделен на фичи (`features/`), каждая из которых имеет свою собственную Clean Architecture (data, domain, presentation).

## 2. Структура Слоев

### 2.1. Слой Domain (Ядро)

*   **Назначение:** Содержит бизнес-правила и логику, не зависящую от Flutter, Firebase или других внешних фреймворков.
*   **Состав:**
    *   **Entities:** Классы, представляющие основные бизнес-сущности (напр., `ChecklistItem`, `Recipe`). Должны быть `immutable` и использовать `equatable`.
    *   **Abstract Repositories:** Абстрактные классы, определяющие контракты (методы) для взаимодействия с данными (напр., `RecipeRepository.getRecipes()`). Реализация находится в слое Data.
    *   **UseCases:** Классы, содержащие основную логику. Выполняют одно конкретное действие, используя методы репозиториев (напр., `GetRemoteRecipesUseCase`, `ToggleChecklistItemUseCase`).

### 2.2. Слой Data (Реализация)

*   **Назначение:** Содержит конкретную реализацию контрактов Domain и работу с внешними источниками.
*   **Состав:**
    *   **DataSources (Remote):** Работа с внешними API (Open-Meteo) и облачными БД (Firestore).
    *   **DataSources (Local):** Работа с локальным кэшем (JSON-файлы, `path_provider`).
    *   **Models:** Классы для парсинга данных из внешних источников (напр., JSON-ответов API, документов Firestore). Должны использовать `json_serializable`.
    *   **Concrete Repositories:** Реализация абстрактных репозиториев, которая выбирает нужный DataSource (например, сначала Local, потом Remote).

### 2.3. Слой Presentation (Интерфейс)

*   **Назначение:** Ответственен за отображение UI, сбор пользовательского ввода и управление состоянием.
*   **Состав:**
    *   **BLoC/Cubit:** Управляет состоянием. Принимает события/вызовы и взаимодействует с **UseCases** из Domain-слоя. Не имеет прямой связи с Repositories или DataSources.
    *   **Pages:** Основные экраны приложения.
    *   **Widgets:** Многоразовые UI-компоненты.

## 3. Управление Состоянием (BLoC)

*   **Принцип:** Каждая крупная функция или экран должна иметь свой BLoC/Cubit.
*   **Задачи BLoC:**
    1.  Получить событие (Event) или вызов функции (Cubit).
    2.  Вызвать соответствующий UseCase (из Domain).
    3.  Обработать результат (Success/Failure) от UseCase.
    4.  Выдать новое состояние (State) в UI.
*   **Naming Convention:**
    *   Events: `...Event` (напр., `LoadRecipesEvent`)
    *   States: `...State` (напр., `RecipesLoadingState`, `RecipesLoadedState`)
    *   BLoC: `...Bloc` или `...Cubit` (напр., `RecipesCubit`)

## 4. Зависимости (DI)

*   Используется пакет **`get_it`** для управления зависимостями.
*   Все репозитории, DataSources и UseCases должны быть зарегистрированы в `di/di_container.dart`.
*   BLoC/Cubit получает свои UseCases через конструктор.
